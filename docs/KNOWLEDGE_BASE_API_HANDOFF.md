# UNITED: knowledge-base API handoff

Дата перевірки: 20 жовтня 2026. Репозиторій: `Molodoy667/UNITEDUKRAINE`, гілка `main`.

## Статус і межі

Реалізація, міграція, адмінка та український корпус готові. 55 категорій і 256 статей успішно імпортовано й перевірено в **окремій тимчасовій локальній MariaDB 11.4**, не в робочій базі. Це не підтверджує деплой чи роботу нового API на production-домені. Коміт і push погоджені власником; їх фактичний результат перевіряється за Git, а стан production-міграції та нового API потрібно перевірити окремо після деплою.

Код гри, ASI/DLL, manifest, клієнтський JavaScript, CDN override та окремий проєкт лаунчера не змінювалися. Їх підключення — наступний окремий етап після публікації й перевірки API.

Власник підтвердив **публікацію всього перекладу при імпорті**. Сторонні правила й числа збережено, а не видано за перевірені правила UNITED. Перед використанням прочитати `docs/KNOWLEDGE_SOURCE_REVIEW.md` і всі `data/knowledge/ua/review-*.json`.

## Точні маршрути та DTO

Запланована база на основному домені: `https://united-rp.com.ua/api/knowledge-base`.
На іншому домені цього ж Vercel-деплою змінюється тільки origin. Клієнт повинен додавати `/categories`, `/posts/{categoryId}` чи `/search`, не викликати голу базову адресу як список.

| Запит | Успішна відповідь |
| --- | --- |
| `GET /categories` | Масив усіх доступних опублікованих категорій `{id,parent,title,position}` |
| `GET /posts/48` | Масив усіх опублікованих статей **саме** категорії 48, без статей дочірніх категорій |
| `GET /search?query=досвід` | Масив збігів у заголовку або тексті серед доступних опублікованих статей |

Успіх — HTTP 200, верхній рівень **масив**, без `data`, `items`, `total` чи pagination. У публічному пошуку немає прихованого LIMIT; тест підтверджує 105 збігів. Порожній query, відсутність збігів та відсутня/прихована категорія повертають `[]`. Query обрізається по краях, максимум 200 символів; `%`, `_`, `!` шукаються буквально, SQL параметризований. Пошук нечутливий до регістру за `utf8mb4_unicode_ci`, перевірений на `ґ`, `Ї` та апострофах.

Фрагмент реального перекладеного seed для `/categories` (не повна відповідь з 55 записів):

```json
[
  {"id":1,"parent":0,"title":"Основи гри","position":0}
]
```

Реальний об'єкт статті 233, який входить у відповідь `/posts/48` (у категорії є й інші статті):

```json
[
  {
    "id":233,
    "category_id":48,
    "client":"all",
    "title":"Яка максимальна сума ставки?",
    "content":"Максимальна сума ставки становить 5.000.000 рублів.",
    "position":0
  }
]
```

Це вихідна стороння ціна, **не підтверджений ліміт UNITED**. DTO завжди містить рівно шість полів: `id`, `category_id`, `client`, `title`, `content`, `position`. `client` збережено як `all` або `pc`; API його повертає, але не відфільтровує замість клієнта. ID і position — JSON numbers. Корінь категорій має `parent:0`. Сортування: `position ASC,id ASC`.

`content` — plain text, не HTML/Markdown. Оригінальні CRLF/LF та списки збережено; JSON кодує переноси як `\r\n`/`\n`, після декодування це справжні переноси. У вебінтерфейсі використовувати textContent/React text і `white-space:pre-wrap`, не innerHTML. Кодування `application/json; charset=utf-8`.

Помилки — JSON `{error,message}`, не порожній масив і не HTML. Невідомий маршрут/гола база — 404, завеликий query/некоректний числовий ID — 400, недоступна БД — 503, спроба запису — 405. HEAD повертає відповідний статус і заголовки без тіла, OPTIONS — 204 без звернення до БД.

## CORS, кеш і видимість

Публічне читання не потребує авторизації. `Access-Control-Allow-Origin: *`; дозволено GET, HEAD, OPTIONS та заголовки Accept, Content-Type, X-Unity-Version. Credentials не дозволені й клієнту не потрібні. Для адмінки wildcard CORS не застосовується.

На публічних відповідях, включно з помилками, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`. Немає програмного кешу списку. Збережена публікація видима наступному запиту; уже відкритий клієнт повинен повторно завантажити дані. Категорії й статті читаються в одному read-only REPEATABLE READ snapshot, щоб одночасне редагування не змішувало різні стани видимості.

Чернетка/видалення будь-якого предка приховує все піддерево, його статті й результати пошуку. Порожні опубліковані контейнери, зокрема початкові категорії 12 і 36, збережені й повертаються; `/posts/36` спочатку `[]`. Цикли та невідомі батьки не допускаються; пошкоджені ієрархії fail-closed.

## Адмінка

Після входу ігровим акаунтом з актуальним `accounts_1101.admin = 12`:
`/account?tab=admin&module=knowledge` → «База знань», четвертий блок адмінки.

Є створення й редагування категорій/підкатегорій, вибір батька, порядок, публікація, створення й редагування статей, client all/pc, переміщення між категоріями зі збереженням ID, plain-text preview, пошук, розміри сторінок 20/50/100 і пагінація. Адмінська пагінація **не є обмеженням публічного API**.

Видалення м'яке, через підтвердження та кошик. Категорію з активними дочірніми категоріями/статтями сервер відхиляє 409 з кількістю залежностей; спочатку перенести/видалити їх. Каскадного знищення немає. Відновлення — чернеткою; батьківську категорію слід відновити першою. ID і текст не губляться.

Приватні endpoint-и: `GET /api/admin?action=kb-categories&state=active|trash`, `GET /api/admin?action=kb-posts&state=active|trash&q=...&categoryId=...&page=1&size=20`. Записи: POST на той же endpoint з action `kb-category-save`, `kb-category-delete`, `kb-category-restore`, `kb-post-save`, `kb-post-delete`, `kb-post-restore`.

Save-body категорії: `{requestId,id,version,category:{parent,title,position,published}}`; статті: `{requestId,id,version,post:{category_id,client,title,content,position,published}}`. Для створення `id:null,version:0`; видалення/відновлення — `{requestId,id,version}`. UUID v4, ігрова session cookie і `X-Account-Csrf` обов'язкові. Origin/JSON перевіряються. Назва категорії до 180, заголовок статті до 240, текст до 30000 символів з додатковою загальною межею JSON-body 64 KiB. Порядок — невід'ємний INT, published — boolean.

Права повторно перевіряються під блокуванням акаунта перед записом. Є optimistic version (409 замість перезапису чужої правки), атомарний аудит `site_content_audit`, спільний ліміт CMS 120 змін за 15 хвилин на адміністратора та UUID-idempotency. Зміни ієрархії серіалізуються окремим lock-row з current locking reads, не застарілим transaction snapshot.

Після невизначеної помилки зв'язку редактор блокує зміну полів і дозволяє повторити той самий запит з тим самим UUID. Захист зберігається при перемиканні панелей у відкритій вкладці, **не після повного перезавантаження сторінки**. Якщо перезавантажили вкладку після обриву, спочатку перевірити список/журнал, а не створювати матеріал повторно. Секрет CSRF не зберігається в localStorage.

## БД, джерело та повторний деплой

`migrations/011_knowledge_base.sql` створює окремі InnoDB-таблиці `site_kb_categories`, `site_kb_posts`, `site_kb_imports`, `site_knowledge_lock`. Ця міграція не змінює поля/баланси ігрових акаунтів. Старі міграції проєкту виконуються як раніше; це не дозвіл повторно застосовувати вже виконані SQL вручну.

`lib/forum/migrate.js` під наявним migration advisory lock застосовує numbered SQL і викликає `seedKnowledge`. Штатний `npm run deploy:build` вже виконує `npm run forum:migrate` перед `npm run build`. Потрібні наявні DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD і DDL/DML-права; нових секретів для knowledge API немає. Не імпортувати повний дамп гравців.

Дані: `data/knowledge/source/{categories.original.json,posts.original.json,source-manifest.json}` — точні оригінали; `data/knowledge/ua/categories.json` та `posts-1.json` … `posts-6.json` — український seed. Джерело наданого корпусу: `https://service.hassleconnect.com/api/knowledge-base`, не live dependency API. Архів передачі SHA-256: `da54dc84667e26e2b5b40328b8a024497b41a3d07f447047b4eeb5081f636b2d`.

Seed-key `hassle-ua-20261020-v1`, checksum перекладеного `{categories,posts}`:
`b037bd506e08de5e4624365d01bc59e12c55b6f24eee15f00548f43954589e66`.

Імпорт усіх 55/256 записів — одна транзакція зі збереженням оригінальних ID, parent/category_id, client і position. Усі published=1 за підтвердженням власника. Існуючі редакторські записи з конфліктним ID не перезаписуються: імпорт зупиняється. Ledger забезпечує повторний запуск без дублікатів, відновлення видаленого або перезапису правок. Зміна вже застосованого seed з тим самим ключем зупиняє міграцію; потрібен новий явно погоджений імпорт, не редагування минулого. База після імпорту є джерелом істини; читання API не залежить від JSON-файлів або чужого сервісу.

## Перевірки та публікація

Локальні команди:

```text
npm run knowledge:validate
npm run test:knowledge
node tests/design.test.mjs
npm run build
```

DB integration: `npm run test:knowledge:integration` потребує окремої loopback MariaDB, `ROULETTE_TEST_DB_PORT` (не 3306), `ROULETTE_TEST_DB_PASSWORD`. Тест створює й прибирає лише випадкову `roulette_test_<hex>` БД, не завантажує production .env. Перевірено повний імпорт, незмінність ігрових записів, права/CSRF/Origin, UUID retry, конфлікти версій, цикл, приховування піддерева, пошук/105 результатів, пагінацію адмінки, переміщення, кошик/відновлення, повторний seed, rollback при збої аудиту та snapshot-конкурентність.

Результати фінального прогону: knowledge unit/retry — 9; knowledge DB/HTTP integration — 14; SSR/design — 17; account unit — 16; admin unit — 7; site unit — 4; Discord unit/HTTP — 8; forum unit — 9. Усі ці перевірки пройшли. Інтеграції CMS — 10, фото новин — 8, admin — 18, roulette — 13 також пройшли.

Окреме застереження регресійного прогону: у старому `tests/forum.integration.mjs` пройшли 16 із 17 вкладених сценаріїв; `opt-in mail outbox sends generic notices and rechecks private access` повернув `sent:0` замість `1` на рядку 299. Той самий збій відтворено в ізольованій копії з вимкненими міграцією 011 та імпортом knowledge. Тобто він відтворюється незалежно від підключення бази знань; точна причина в поштовому сценарії ще не встановлена. Поштову логіку в цій задачі не змінено. Загальний статус усіх тестів проєкту не слід оголошувати зеленим.

Після commit/push і завершення деплою перевірити **на фактичному домені** всі три URL, 55/256 записів, CORS/OPTIONS/HEAD, невідомий маршрут як JSON 404 (не SPA), адмінське створення/публікацію тестового матеріалу і роботу API у цільовому клієнті. Vercel rewrites й middleware/CDN на живому домені ще не перевірено. Нових Vercel functions не додається: маршрути йдуть через наявний `/api/site`, загальна кількість JS-функцій залишається 12.

Візуальна та інтерактивна перевірка браузером на production не виконувалась; SSR-тести перевіряють структуру/екранування, а не реальну розкладку на кожному екрані. Відповідність усіх правил імпорту грі й незалежна редактура кожного речення не підтверджені.
